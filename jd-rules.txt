# ============================================================
# JD 规则过滤（对岗位描述 postDescription 做判定）
# ============================================================
# 生效时机：每次点「开始投递」时重新读取本文件 —— 改完直接重跑任务即生效，
#          不需要重启程序，也不需要重新编译。
# 文件位置：优先读项目根目录（就是本文件），找不到才会去读 classpath 里的同名文件。
#
# ---------- 语法 ----------
#   规则头：[动作] 名称 阈值        （阈值可省略，默认 1）
#   词    ：紧跟规则头，一行一个
#   空行、以及 # 开头的行都会被忽略
#
#   三种动作：
#     reject  = 命中（命中词数 ≥ 阈值）→ 直接跳过，不投递
#     require = 必须命中（命中词数 ≥ 阈值）→ 否则跳过，不投递
#     warn    = 命中只记提示（写进 boss_data.filter_note），照常投递
#               —— 用来标记「可以具体谈」的条件
#
#   阈值统计的是「命中了多少个不同的词」：遍历词表时每个词最多计一次，
#   所以 JD 里把同一个词重复提很多遍并不会灌水凑满阈值。
#
# ---------- 判定顺序 ----------
#   1) JD 为空              → 放行并打日志（fail-open：宁可多投也不误杀）
#   2) 任一 reject 规则命中  → 跳过
#   3) 任一 require 未达标   → 跳过
#   4) warn 规则命中         → 仅提示，仍投递
#
# ---------- 重要提醒 ----------
#   匹配方式是「包含」，而 JD 是几千字的长文本，很容易误伤，例如：
#     「销售」    会命中「配合销售部门出报表」（其实是好岗位）
#     「数据分析」会命中「无需数据分析经验」（意思正好相反）
#   所以请优先写【短语 / 否定式说法】，而不是笼统的行业词。
#
#   建议节奏：先只放开 reject 这一块，跑一轮后看日志里有多少「被过滤：」记录、
#   有没有误伤，确认之后再逐步放开 require。
# ============================================================
